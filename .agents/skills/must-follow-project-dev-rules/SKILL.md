# ra2-explorer 项目开发强制准则

凡是会修改本仓库代码、配置、测试或文档的任务，都必须执行以下流程。用户针对当前任务的明确要求优先。

## 开发命令行环境

1. 开发、构建、测试、检查、运行、文件操作、项目脚本和 Git 操作全部强制使用本机 `cmd.exe`。
2. `git status`、`git diff`、`git add`、`git commit` 等 Git 命令直接在 `cmd.exe` 中执行，不得为 Git 单独启动 Git Bash。
3. 不使用 PowerShell 或 Git Bash 作为项目开发命令行，避免编码、转义、命令别名和脚本语义差异影响结果。
4. 命令、路径和文档示例必须使用 `cmd.exe` 语法；同一项操作不得跨 shell 拼接。

## 命令执行效率与进程管理

1. 每条命令默认只承担一个明确目的，并限定工作目录、目标路径、输出量和等待时间；优先使用 `rg` 的单一关键词和精确路径，避免在 `cmd.exe` 中堆叠易碎的引号、正则交替、管道或超长单行脚本。
2. 禁止无目标地递归枚举用户目录、系统目录或整个磁盘。查找程序或文件时，依次使用 `where`、已知安装目录、项目清单和有限候选路径；输出只保留判断所需的最少上下文。
3. 同一种 shell 转义或命令拼装方式失败一次后必须换用更稳健的策略，不得继续尝试近似变体。复杂诊断应改用仓库现有 CLI，或通过 `apply_patch` 创建范围明确的一次性脚本，并在使用后清理。
4. 启动服务器、监听器或其他长驻进程时，必须记录端口、PID 或会话标识；首次只短暂等待启动证据，按需轮询，并在验证结束后立即回收临时进程。禁止用长时间阻塞等待代替状态检查。
5. 执行命令前先明确成功证据和停止条件。已经得到充分证据后不得继续探索无关环境、重复构建、重复读取大文件或输出完整递归列表。
6. 仅并行执行彼此独立、耗时可控的只读检查；不得并行执行会竞争同一数据库、缓存、端口或工作树的变更命令。

## 快速迭代与最小验证

1. 先阅读相关实现、现有文档、最近提交和当前 diff，再确定最小改动面。
2. 只运行能证明本次改动的最小定向检查；代码或配置未变化时，不重复相同检查。
3. 只有跨模块风险、发布门、公共合同变化或用户明确要求时，才运行完整测试套件。
4. 昂贵的 GPU、模型下载和全量媒体编解码，默认只做一个最小且有代表性的资格化；已有有效证据可直接复用。
5. 删除或合并重复、脆弱、只验证实现细节或固定文案而不保护真实合同的测试。不得仅为缩短时间删除有价值的回归测试。
6. 常规代码与配置开发不得新增以文件 hash 为核心的变更检测、缓存失效或测试断言；优先验证结构、版本、字段和可观察行为。正常迭代也不得反复计算大模型或媒体文件 hash。
7. 默认不得在代码或项目流程中新增门控、测试或检测。只有它能保护已经发生过的用户可见故障、安全边界或不可恢复数据，并且现有检查无法覆盖时才允许新增；必须选择维护成本最低的行为验证，禁止推测性阈值、重复门控、固定文案断言和实现细节检测。修改相关区域时主动合并或移除已经失去真实保护价值的旧检查。

## 大文件下载网络边界

1. 模型权重及其他大体积模型 payload 不得经过本机 `11111` 或 `11119` 代理；模型解析和下载子进程必须同时清除大小写 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`，设置 `NO_PROXY=*`，并让 Python 客户端使用空 `ProxyHandler`、aria2 使用 `--all-proxy=` 与 `--no-proxy=*`。
2. Hugging Face 模型优先通过 `HF_ENDPOINT=https://hf-mirror.com` 和固定 revision 直连。镜像不可用时不得静默回退到代理；应明确失败，或切换到已经登记并验证的其他直连镜像。
3. 允许使用 ModelScope 作为模型直连下载源，但必须把 provider、repository 和 revision/branch 写入供应链 manifest 或证据；下载前逐文件核对 manifest 声明的大小与内容 digest，下载完成后再做完整 digest 校验，通过后才能发布到内容寻址 store 和运行 view。ModelScope 的可变分支不能替代 digest pin。
4. 执行大模型同步时必须用进程级连接证据（如 `ss -tnp`）确认下载进程没有连接 `127.0.0.1:11111` 或 `127.0.0.1:11119`；只看到主机上其他进程使用代理不构成下载违规。记录结果时不得输出代理凭据或带签名的临时下载 URL。
5. 这里要求的下载后完整 digest 属于模型供应链安全合同，不受“常规迭代避免重复计算大文件 hash”规则限制；已经发布且无损坏迹象的模型仍只做快速尺寸校验。

## 游戏源与派生产物隔离

1. `.runtime\RA2MD` 是用户提供的官方游戏安装，只能静态读取；不得修改、覆盖、重命名、移动或删除其中任何原始文件，也不得运行该目录及其子目录中的任何 EXE。
2. 解包文件、解析缓存、格式转换结果、缩略图、派生索引和其他可复用处理产物统一写入 `.runtime\RA2MD-Ext`。不得为了缩短实现把派生产物写回 `.runtime\RA2MD`，也不得把二者混用为同一个可写数据根。
3. 扫描原始游戏源时必须排除 `.runtime\RA2MD-Ext` 及其他已登记的派生产物根，防止转换结果被重复识别为原始资产。产物目录结构应由稳定资产标识和格式组织，并在必要时记录生成器版本或参数，以支持增量复用和安全重建。
4. 删除或重建派生产物前必须先解析并核对目标绝对路径确实位于 `.runtime\RA2MD-Ext`；不得把清理范围扩大到 `.runtime\RA2MD`、项目根或其他未明确授权目录。

## 稳定阶段必须提交

当一个阶段的目标已经实现、最小定向检查通过、相关文档与当前行为一致时，该阶段视为稳定：

1. 检查 `git status` 和完整 diff，区分本阶段改动与用户已有改动。
2. 只显式暂存本阶段文件，不提交秘密、缓存、生成媒体、临时诊断或失败实验产物。
3. 用一行祈使式 commit message 概括阶段结果，然后执行 `git commit`。消息正文只包含自然语言内容，
   不得把命令行双引号写进提交标题，也不得用短杠代替词语之间的自然空格；`cmd.exe` 引号处理不稳时，
   应使用临时消息文件配合 `git commit -F`，提交后立即删除临时文件。一个稳定阶段不得长期留在未提交工作区。
4. 不把无关阶段塞进同一提交；未稳定的阶段不得为了满足形式要求提前提交。
5. 除非用户明确要求，不 amend、不重写历史、不覆盖他人的提交。
6. 一次用户任务可能同时包含多个可独立稳定的改动。提交前必须查看 diff 规模，并按用户可见能力、
   模块边界和内容归属拆成合理的多个小提交；每个提交只表达一个完整、可验证的主目的。不得仅因需求
   是一次性提出，就把彼此独立的代码、配置、文档或清理工作合并成一个过大的提交；对应某项代码合同
   的测试和文档应跟随该项代码，不得为了追求文件分类而拆散同一个可运行阶段。
7. 开发过程中即使会持续收到新需求，已完成且验证通过的边界功能也必须立即提交，不等待整段对话或
   所有后续需求结束。新需求与当前未稳定阶段同属一个功能边界时可一并收敛；若属于无关或新的功能边界，
   先提交已稳定改动，再开始新阶段，避免上下文切换污染已完成工作。
8. 稳定阶段不是抢救性快照。类型检查、针对性测试或真实主路径验收仍失败时，必须继续收敛当前阶段，
   不得为了快速清空工作区而提交半成品。
9. 多个阶段提交应尽可能降低相互冲突：先提交依赖较少的规则、数据合同或独立组件，再提交依赖它们的
   行为；避免多个提交反复改写同一段代码。若两个改动必须共同存在才能编译或运行，应合并为一个内聚
   提交，而不是制造不可构建的中间历史。

## 文档与经验同步

1. 在同一稳定阶段更新最接近改动的 README、操作、工作流、基准或架构文档。
2. 文档必须描述当前真实合同；发现过时命令、版本、默认值或要求时，直接修正或移除。仍有复现价值的旧信息必须明确标成历史证据，不得混写成当前状态。
3. 记录可复用的原因、失败路径、资源边界和排障方法；不记录无长期价值的逐步流水账。
4. 提交前核对文档中的路径、示例命令、版本和配置名是否仍存在。

## 产品表达与工程文本

1. 前端只展示完成操作、理解输入输出或处理错误所必需的标签、状态和提示。默认不展示实现说明、
   开发过程、临时需求状态、重复上下文或对功能没有影响的解释性旁白；能由布局、控件名称和当前值
   清楚表达的内容不再追加说明文字。
2. 不把用户对话中的口语、临时命名或一次性验收措辞直接固化为 UI、接口字段、代码标识或文档。
   先提炼稳定的产品概念与合同，并沿用项目现有术语。必要的错误信息必须简短、具体且可操作。
3. 代码注释只用于解释无法从类型、命名、结构或测试看出的长期不变量、风险和取舍；不复述代码，
   不记录需求讨论、修改流水账、临时方案或当前进度。优先通过清晰命名和小型函数表达意图。
4. 文档聚焦当前可执行合同、稳定架构、操作边界和仍有复用价值的证据；不写任务汇报、会话记录、
   临时状态或无长期价值的解释。历史基准或事故证据只有在继续影响决策时才保留并明确标注时间与范围。
5. 新增任何面向用户或仓库维护者的文字前，先确认它能支持一个实际动作、消除真实歧义或防止已知
   失败；否则省略。修改相关区域时一并删除已经失去这些作用的旧文字。

## 前端组件与布局

任何前端 UI 的设计、实现、重构、评审或浏览器测试，都必须同时完整读取并遵循
`../must-follow-ui-design-rules/SKILL.md`。本节只保留跨项目开发流程所需的基础合同；更具体的信息架构、
外观、滚动、响应式、持久化、媒体预览和 VXL 浏览规则以该 UI skill 为准。

1. 新增或修改按钮、输入框、选择器、勾选项、菜单和弹层前，先检查同一区域及相邻流程已经使用的
   DOM 结构、组件类、设计变量和交互状态；复用既有控件高度、内边距、圆角、字号、边框以及
   hover、focus、disabled、loading 语义，不为单个需求另造一套样式或强调色。尤其需要注意组件和文本字体的对齐。
2. 先确定信息层级和操作顺序，再安排网格或弹性布局。关联的标签和值、选择项和触发按钮应靠近并
   对齐；控件宽度随内容和可用空间分配，不用无依据的固定宽度、占位列或空白填补布局。紧凑区域
   必须检查中文长选项、数字输入、窄容器和换行后的基线与间距。
3. 固定且必选的值应呈现为清晰的只读或禁用状态；互斥项、可选项和主次操作必须从控件本身表达
   关系。不要用额外注释、开发解释、临时状态文字或重复提示弥补含混的控件命名和布局。
4. 配色只使用项目现有变量和稳定的语义状态。普通操作、主操作、危险操作、选中、错误和处理中
   状态不得混用；除非产品已有相同语义，不给一次性功能引入新的高亮色、阴影或视觉层级。
5. UI 改动的最小验收应覆盖与本次变更相关的默认态、选中态、禁用或处理中状态、打开和关闭弹层、
   长文本及项目支持的窄宽度。检查可见对齐、异常空白、截断、横向溢出、布局跳动、焦点可达性，
   以及容器嵌套造成的双滚动条；同时与相邻现有控件做视觉和交互一致性对照。
6. 回归测试保护实际行为、数据合同和可访问语义，不锁定整段 UI 文案或偶然的 DOM/CSS 实现。
   只有已发生且容易复发的用户可见布局故障，才增加最小的结构性断言。
7. 正文、列表主信息和表单控件的最终渲染字号不得小于 12px；辅助元数据不得小于 11px。只有纯装饰
   标记可使用 10px，且不得承载操作、状态或区分资源所必需的信息。窄屏适配不得通过继续缩小字体
   解决空间不足，应改用换行、隐藏次要列或重排布局。
8. 任何承载超出可视区域内容的资产列表、网格或详情面板都必须提供稳定且可见的滚动条，并保留
   滚动条槽位以避免布局跳动。验收至少覆盖鼠标滚轮、拖动滚动条、键盘滚动和窄窗口；不得仅依赖
   操作系统可能自动隐藏的覆盖式滚动条。
9. 资产和资源集合必须同时提供 list 与 grid 视图。两种视图复用同一查询、筛选、选中和加载状态：
   list 用于高密度属性比较，grid 用于图像、模型、声音等内容识别；切换视图不得重新解释数据或丢失
   当前选择。不同格式应采用适合内容的卡片、预览或播放器，不把所有类型强塞进同一种行模板。
10. 页面不得展示只面向开发者的实现说明、临时进度、验收话术、重复位置列、无操作价值的完整路径
    或用于填补空白的解释性文本。路径、来源和技术标识只在用户执行导出、定位、排障或确认覆盖来源
    时按需呈现；修改相邻页面时一并清理已经失去动作价值的旧文本。
11. 资产与语义实体使用同一套树状导航；单位类型作为“单位”的子节点，媒体和可选底层格式作为同级
    内容节点。不得再用“资源 / 单位”标签切换制造两套分类，也不得用原始模型分类重复语义单位入口。
12. 中间集合视图应按当前内容类型提供紧凑的标签筛选和有效排序。筛选与排序必须复用查询、分页、
    list/grid 和选中状态的数据合同；不得只重排当前可见页而让结果计数、后续分页或详情选择失真。
13. 详情区默认采用集合在上、宽屏详情在下的布局，同时在显示设置中提供集合与窄屏详情左右排列的
    切换；独立详情窗口默认采用宽屏排版并拥有自身可见滚动条。主工作台不设置顶部工具栏，页面名称
    位于左栏顶部，显示设置固定在左栏底部；索引状态、添加目录和重新扫描不得作为常驻页面控件。
14. 左侧树状导航必须支持收起为仍可通过图标、title 和可访问名称操作的窄栏；桌面 list 视图默认用
    双列提高密度。上下和左右详情布局都必须提供可拖动、可键盘操作的分隔条，详情标题保持单行并放在
    信息列上方。导航状态、详情尺寸、浏览上下文、当前选择和列表/详情滚动位置必须在刷新后恢复。
    规则属性依据内容宽度在一至三列间排布；缺少原文或中文时不得渲染无意义的空占位行。

## 隐私配置

1. `.secrets\local.env` 中包含了项目中可能用到的隐私配置。你需要保证这些隐私配置不被泄露。对于新的需要保护的隐私配置和本地配置，也应当放到这个文件中。
2. 代码、测试、提交信息和文档不得写入个人邮箱、本机用户名、用户目录、工作区绝对路径、访问令牌、
   密码、私钥或带凭据的 URL；示例使用相对路径、环境变量或明显的占位值。本地游戏文件、派生结果、
   隐私扫描报告和发行输出不得进入 Git。
3. 当前 clone 必须通过 `scripts\setup_dev.cmd` 启用 `.githooks`。每次提交由 pre-commit 钩子扫描暂存区，
   不得使用 `--no-verify` 绕过；提交前的人工检查仍需确认 diff 没有不适合公开的业务数据或二进制素材。
4. 涉及公开发布时，除当前树检查外必须运行完整可达历史扫描。报告不得回显秘密原文，只能输出规则、
   位置和不可逆指纹。发现真实凭据时先撤销或轮换；只有用户明确授权并确认精确范围后才能改写历史。

## 交付说明

最终交付必须列出阶段 commit、实际运行的最小验证、因已有证据而没有重复运行的检查，以及尚存风险或需用户决定的运行时操作。
